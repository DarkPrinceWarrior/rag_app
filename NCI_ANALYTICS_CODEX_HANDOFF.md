## 4. A100 и обязательный процесс доставки

- SSH: `ssh a100` (`root@192.168.101.12`, доступ из офиса/VPN);
- серверный каталог: `/root/projects/nsi_analytics`;
- адрес стенда: `http://192.168.101.12:8089/`;
- Compose: `/root/projects/nsi_analytics/backend/deploy/a100/docker-compose.yml`;
- защищённое окружение: `/etc/nci-analytics/nci-analytics.env`;
- рабочая ветка обоих серверных репозиториев: `ruslan_agent`.

Разрешён только однонаправленный процесс:

```text
WSL: edit -> focused checks -> commit -> push
GitLab
A100: clean checkout -> git pull --ff-only -> build -> migrate -> up -> smoke
```

Запрещено:

- редактировать исходный код непосредственно на A100;
- копировать изменённый код на A100 через SCP;
- делать force-push, reset серверной рабочей копии или переписывать историю;
- выполнять `docker compose down --volumes` при обычном обновлении;
- печатать, копировать в Git или добавлять в этот файл секреты из `/etc`.

Если серверная рабочая копия грязная или не может обновиться fast-forward,
остановиться, зафиксировать факты и выяснить происхождение изменений. Не
сбрасывать их автоматически.

Обычное обновление после push:

```bash
ssh a100
git -C /root/projects/nsi_analytics/frontend pull --ff-only
git -C /root/projects/nsi_analytics/backend pull --ff-only
cd /root/projects/nsi_analytics/backend

docker compose \
  --env-file /etc/nci-analytics/nci-analytics.env \
  -f deploy/a100/docker-compose.yml \
  build backend frontend

docker compose \
  --env-file /etc/nci-analytics/nci-analytics.env \
  -f deploy/a100/docker-compose.yml \
  run --rm migrate

docker compose \
  --env-file /etc/nci-analytics/nci-analytics.env \
  -f deploy/a100/docker-compose.yml \
  up -d --remove-orphans
```

После обновления проверить `docker compose ps`, restart count, логи,
`/healthz`, OpenAPI, UI через Playwright и равенство SHA в WSL/GitLab/A100.
Пароли тестовых пользователей в репозитории не хранить; для smoke получить
актуальные учётные данные у владельца или из разрешённого защищённого канала.

## 5. Что брать из DocRAGenslate как референс агента

Перед проектированием агентного функционала NCI изучить:

- `src/rag_app/rag/agent.py` — классификация запроса и цикл агента;
- `src/rag_app/rag/tools.py` — ограниченные инструменты агента и накопление
  проверяемых источников;
- `src/rag_app/rag/chat.py` — подготовка контекста, бюджет окна и цитаты;
- `src/rag_app/api/routes/chat.py` — FastAPI/SSE, сессии, права и аудит;
- `web/src/routes/chat.tsx` — UX чата, история, область источников, потоковые
  шаги и панель цитат;
- `web/src/lib/sse.ts` — клиент потокового протокола.

Переносимые принципы:

- агент отвечает только в пределах прав пользователя и выбранной области;
- каждое число и вывод должны быть прослеживаемы до данных NCI;
- инструменты агента имеют явные схемы, лимиты и fail-closed поведение;
- длинная операция показывает прогресс потоково, а не блокирует интерфейс;
- история, аудит, ошибки и отмена проектируются сразу;
- интерфейс объясняет источник, период, фильтры и метод расчёта;
- отсутствие данных показывается честно, без выдуманных значений.

DocRAGenslate использует React, а NCI — SvelteKit. Переносить архитектурную и
UX-идею, но реализовывать её нативно средствами существующего стека NCI.

## 6. Известные ограничения стенда

- Приложение, PostgreSQL, backend, frontend и Nginx на A100 работали и были
  healthy при передаче; UI, `/healthz` и `/api/openapi.json` отвечали HTTP 200.
- Корпоративное имя `srv-1capp-urps.corp.tatneft.tatar` на A100 сейчас не
  разрешается DNS. Поэтому интеграция МТР может возвращать пустые данные. Это
  внешнее ограничение, а не основание подменять данные на frontend.
- A100 является общим сервером. Не останавливать и не перенастраивать сервисы
  `rag_app`, GPU-модели и контейнеры других проектов без явной задачи.
- При последней проверке на системном диске оставалось около 76 ГБ. Не выполнять
  бездумные `--no-cache`, массовую очистку Docker или удаление общих образов.
