# Проверка изоляции 10 учётных записей, 2026-07-13

## Цель и ограничения

Проверка выполнена на действующем A100 production без изменения realm,
клиентов, паролей, ролей и состояний учётных записей. Документы и сообщения чата
не создавались. Bootstrap-данные администратора Keycloak читались только в
память процесса на A100; токены и имена пользователей не сохранялись.

Context7 во время подготовки был недоступен из-за сетевой ошибки. Решение
сверено с официальной документацией Keycloak 26:

- [имперсонация пользователя администратором](https://www.keycloak.org/docs/latest/server_admin/index.html#impersonating-a-user);
- [Admin REST: `POST /users/{user-id}/impersonation`](https://www.keycloak.org/docs-api/latest/rest-api/index.html#_users_resource);
- [обмен токенов](https://www.keycloak.org/securing-apps/token-exchange):
  стандартный V2 не реализует подмену субъекта, а legacy V1 устарел, имеет
  статус preview и нужен для рискованной direct naked impersonation.

Поэтому legacy token exchange не включался. Использован существующий public
client `rag-web`: browser impersonation, затем штатный Authorization Code с
PKCE S256. Созданные успешным прогоном сессии завершались по собственному
refresh token.

## Методика

HTTP-контур для каждого автоматически полученного bearer token:

1. `GET /api/documents` должен вернуть `200`.
2. `GET /api/search` должен вернуть только документы, доступные тому же token.
3. `GET /api/documents/{чужой_id}` должен вернуть `404`.
4. `POST /api/chat?memory=off` с чужим `document_ids` должен вернуть `404` до
   запуска SSE, ретривера и записи сообщения.
5. Smoke-сессия Keycloak завершается, ожидается `204`.

Полностью автоматический PKCE без пользовательского экрана прошли 3 из 11
доступных не-администраторских учётных записей. Для остальных Keycloak вернул
интерактивный OIDC redirect. Чтобы не менять production-аккаунты и не включать
устаревший обмен токенов, применён предусмотренный fallback: 10 реальных
Keycloak subject поочерёдно установлены как principal в production-роль
PostgreSQL `rag_api`. Для каждого проверены GUC `app.user_id` и
`app.is_admin=off`, видимость `documents`, область `chunks` для retrieval и
пустой поиск чужого документа. Транзакции были только на чтение по факту
выполненных запросов; данные не изменялись.

## Результат

| Проверка | Результат |
|---|---:|
| Включённых пользователей Keycloak | 12 |
| Не-администраторских пользователей с ролью `user` | 11 |
| Полный HTTP/OIDC smoke | 3/3 |
| `GET /api/documents` | 3/3: `200` |
| RAG-поиск и проверка доступности результатов | 3/3 |
| Чужой документ | 3/3: `404` |
| Чужая область чата/RAG | 3/3: `404` |
| Завершение smoke-сессии | 3/3: `204` |
| Production RLS principals | 10/10 |
| Пересечения документов между principals | 0 |
| Ошибки области `chunks` retrieval | 0 |

**Итог: проверка пройдена.** Изоляция подтверждена полным HTTP-контуром для
трёх автоматически доступных token и production RLS-контуром для десяти
реальных subject. Ограничение результата: это не 10 полноценных bearer HTTP
сессий; восемь аккаунтов требуют интерактивного шага Keycloak.

**Обновление 14 июля 2026 года:** интерактивное ограничение устранено в
автоматизированном smoke; полный HTTP/OIDC-контур прошёл для 10 из 10 выбранных
неадминистраторских учётных записей. Абзац выше сохранён как результат исходного
прогона 13 июля, а не как текущее ограничение.
